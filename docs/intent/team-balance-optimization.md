# 조건부 팀 편성의 균형 최적화와 탐색 진행 표시

- 확정일: 2026-11-24
- 상태: 의도 확정. 구현 전이며, 새 세션에서 이 문서를 읽고 구현한다.

## 목표 (Why)

같은 팀·다른 팀 조건을 지켰다는 이유만으로 전력 차이가 큰 첫 번째 조합을 반환하는 문제를 줄인다. 조건을 만족하는 여러 후보를 제한 시간 안에 비교하여, 점수 차이를 허용 범위 안에 두면서 포지션 조화가 좋은 조합을 선택한다. 사용자가 탐색 중임을 progress bar로 확인할 수 있게 한다.

## 대상 (Who)

로그인 후 모임에서 참석자와 팀 수, 같은 팀·다른 팀 등의 추가 조건을 입력하여 팀을 나누는 관리자.

## 확정된 동작과 완료 기준 (Success)

### 반드시 지킬 조건

- 선택한 참석자 모두를 정확히 한 번 배정한다. 누락·중복·미선택 선수 포함을 허용하지 않는다.
- 요청한 팀 수를 유지하며, 빈 팀 없이 팀별 인원 차이를 최대 1명으로 유지한다.
- 입력한 같은 팀·다른 팀 조건은 필수 조건이다. 점수나 포지션을 개선하기 위해 위반하지 않는다.
- 포지션 조화는 후보를 비교하는 기준으로 사용한다. 선수 구성상 불가능한 포지션 배치를 필수 조건으로 강제하지 않는다.

### 후보 선택 기준

- 점수 차이는 팀별 평균 점수의 최댓값에서 최솟값을 뺀 값이다. 3팀 이상도 동일하게 적용한다.
- 기준 단위는 화면의 1~10점이다. 내부 rating 1~100 저장 단위와 구분하며, 화면 반올림 이전 값으로 비교한다.
- 탐색한 유효 후보 중 평균 차이가 **0.8 미만**인 후보가 있으면 해당 후보들 안에서 **포지션 조화를 우선**한다. 포지션 조화가 같으면 평균 차이가 더 작은 조합을 선택한다.
- 탐색한 유효 후보가 모두 평균 차이 **0.8 이상**이면 평균 차이가 가장 작은 조합을 선택한다. 평균 차이가 같으면 포지션 조화가 더 좋은 조합을 선택한다.
- 위 예외의 경우 편성을 막지 않고 결과와 함께 **“조건상 균형에 한계가 있습니다”**라는 안내를 제공한다. 전체 조합을 조사해 불가능함을 증명했다는 의미로 안내하지 않는다.
- 전체 이름·생략한 이름 해석 등 기존 조건 해석 기능을 유지한다.

확정 예시:

| 후보 | 포지션 조화 | 팀 평균 | 선택 기준 |
| --- | --- | --- | --- |
| A | 더 고름 | 7.0 : 7.4 | 차이가 0.4이므로 포지션이 덜 고른 B보다 우선할 수 있음 |
| B | 덜 고름 | 7.2 : 7.2 | A의 차이가 0.8 이상이고 B는 0.8 미만이면 B를 선택 |

포지션 조화는 현재 `PositionRoles`의 세부 포지션과 포지션 계열을 참고해 팀별 분포가 고른 정도로 평가한다. 구체적인 평가식은 구현 시 명시하고, 점수 우선순위와 함께 테스트한다.

### 탐색 시간

- 후보 탐색 시간 예산은 **최대 5초**다.
- 첫 번째 유효 조합을 찾았다는 이유만으로 종료하지 않고, 남은 탐색 범위와 시간 안에서 더 좋은 후보를 비교한다.
- 탐색 범위를 모두 확인하여 결과가 확정되면 5초를 채우지 않고 반환할 수 있다.
- 시간 한도에 도달하면 그때까지 찾은 가장 좋은 유효 후보를 반환한다. 전체 최적해는 보장하지 않는다.
- 시간 내 유효 후보를 찾지 못했다면 조건을 위반한 조합을 반환하지 않는다. 탐색 시간 부족과 실제 조건 충돌을 구분해 안내한다.
- 5초는 서버 후보 탐색 예산이며, 조건 해석·네트워크 전송을 포함한 전체 응답 시간이 항상 5초 이하라는 보장은 아니다.

### Progress bar

- 스켈레톤 대신 progress bar를 표시한다.
- 기본 안내 문구는 **“조건에 맞는 균형 잡힌 팀을 찾고 있어요.”**다.
- 진행률은 5초 탐색 예산에 대한 경과 시간을 나타낸다. 가능한 전체 조합 중 검사한 비율이나 최적해에 도달한 확률로 표현하지 않는다.
- 탐색 시간에 따라 바가 차오르며, 결과가 먼저 확정되면 즉시 완료하고 결과 화면으로 전환한다.
- 탐색 시간 예산이 끝나도 응답을 받기 전에는 결과가 완료됐다고 단정하지 않는다. 조건 확인·응답 대기와 후보 탐색 시간을 혼동시키지 않는다.
- 요청 처리 중에는 팀 나누기 버튼을 비활성화하여 중복 실행을 막는다.
- 오류가 발생하면 진행 상태를 종료하고 오류 안내 및 재시도를 제공한다. 이전 요청의 늦은 응답이 다른 모임이나 새 요청의 결과를 덮어쓰지 않도록 한다.

## 제약 조건 (Constraint)

- 현재 Kotlin/Spring Controller-Service-Repository 구조와 Next.js UI 방식을 유지한다.
- 기존 세션 인증·CSRF·관리자 권한·참석자 검증을 유지한다.
- 인원이 많을 때 모든 조합을 끝까지 조사하도록 강제하지 않는다. 구현 방법은 5초 예산과 후보 선택 기준을 충족하는 가장 단순한 방식을 우선한다.
- 포지션 조화를 별도의 자연어 조건으로 입력하지 않아도 이 후보 평가에 포함한다.
- 롤 티어를 포함한 기존 능력치 저장 단위, 표시와 DB 데이터는 보존한다.
- 단순 결과 알림을 사용한다면 기존 공통 Toast 규칙을 따른다. Progress bar는 요청 처리 상태이므로 1초 자동 닫기 규칙을 적용하지 않는다.

## 하지 않을 것 (Out of scope)

- LLM을 통한 조건 해석으로 변경하거나 Claude 팀 분석 방식을 교체하는 작업.
- 능력치·롤 티어·회원 데이터 체계 변경.
- 한글·영문 이름 해석 범위의 추가 확장.
- 모든 인원·팀 수에서 전체 최적해 또는 전수 탐색 완료를 보장하는 작업.
- 게스트 팀 편성 확장, 요청과 무관한 화면 개편 또는 대규모 리팩터링.

## 다음 세션의 검증 기준

- 관계 조건과 팀별 인원을 지키면서 첫 유효 조합보다 좋은 후보를 선택하는 사례를 검증한다.
- 0.8 미만·정확히 0.8·0.8 초과 경계에서 후보 우선순위를 검증한다.
- 같은 인원뿐 아니라 11명·10명처럼 인원이 다른 경우에도 총점 대신 평균 차이로 평가하는지 확인한다.
- 가능한 모든 조합을 확인할 수 있는 작은 사례에서는 완전 탐색 결과와 비교한다.
- 평균 차이가 모두 0.8 이상인 경우 결과 반환 및 한계 안내를 확인한다.
- 5초 예산, 조기 완료, 유효 후보 미발견, 조건 충돌을 각각 검증한다.
- UI에서 progress bar, 중복 실행 방지, 조기 응답, 오류 복구와 늦은 응답 처리를 확인한다. 실제 화면 검증과 자동 테스트 결과를 구분해 보고한다.

## 재현 근거

현재 `TeamBalancer`는 조건을 만족하는 첫 조합에서 종료하며, 최종 후보 점수 비교나 배정 후 개선 과정이 없다. 기존 알고리즘을 직접 실행하고 같은 필수 조건 아래의 모든 2팀 조합과 비교했을 때 다음 사례를 확인했다. 점수는 화면 단위다.

| 참석자 구성·조건 | 현재 총점 | 같은 조건으로 가능한 총점 |
| --- | --- | --- |
| 레이커스 fixture에서 Adou Thiero를 제외한 20명, Hardy·Vanderbilt 같은 팀 | 70 : 74 | 72 : 72 |
| fixture 참석자 14명, Bronny·Ziaire 같은 팀 | 52 : 59 | 55 : 56 |
| fixture 참석자 14명, Sexton·Looney 다른 팀 | 57 : 54 | 55 : 56 |

이 표는 개선 목표의 근거이며, 새 구현의 완료 또는 성능 검증 결과가 아니다.
